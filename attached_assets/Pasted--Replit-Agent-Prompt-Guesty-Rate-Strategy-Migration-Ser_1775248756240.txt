# Replit Agent Prompt: Guesty Rate Strategy Migration Service

## Project Overview

Build a **Node.js/TypeScript microservice** called `guesty-rate-strategy-migrator` that programmatically copies Rate Strategies from one Guesty account to another using **Playwright** for browser automation (UI-driven, since the Guesty Open API has no `POST /rate-strategies` endpoint). The service must be production-grade, secure, and deployable as a background job in a SaaS environment.

---

## Tech Stack

- **Runtime:** Node.js 20+ with TypeScript
- **Browser Automation:** `@playwright/test` (Microsoft Playwright — NOT Puppeteer)
- **HTTP API Layer:** `express` (lightweight REST endpoint to trigger migrations)
- **Secret Management:** Environment variables only — never hardcoded credentials, never logged
- **Queue/Job Management:** `bull` with Redis for async job processing
- **Logging:** `pino` (structured JSON logging, credentials automatically redacted)
- **Validation:** `zod` for input schema validation
- **Package Manager:** `npm`

---

## Security Requirements (Non-Negotiable)

1. **No credentials in code or logs** — all Guesty usernames/passwords and API keys must come from environment variables or be passed as encrypted job payloads
2. **Credentials never logged** — use `pino` with a `redact` config to strip `password`, `email`, `token`, `clientSecret`, `clientId` fields from all log output
3. **Playwright runs headless** in production (`headless: true`) — no GUI, no screenshots saved to disk unless a migration fails (then save to `/tmp` only, deleted after 24h)
4. **Browser context isolation** — each migration job gets its own isolated `BrowserContext` with no shared cookies or storage between jobs
5. **No `--no-sandbox` flag** unless running inside a Docker container with a non-root user and documented justification
6. **Input validation** on all API endpoints using `zod` — reject malformed requests before any browser is launched
7. **Rate limiting** on the REST API using `express-rate-limit` — max 5 migration requests per minute per IP
8. **Timeout enforcement** — individual Playwright actions timeout at 15 seconds; full migration jobs timeout at 10 minutes
9. **Job payload encryption** — if credentials are stored in Bull queue, encrypt them using `crypto.createCipheriv` with AES-256-GCM before enqueuing, decrypt inside the worker

## Step 1 — Guesty Open API: Extract Rate Strategies

In `src/api-client/guestyOpenApi.ts`:

- Authenticate to the Guesty Open API using OAuth2 client credentials:
  - `POST https://open-api.guesty.com/oauth2/token`
  - Body: `{ clientId, clientSecret }`
  - Token is valid 24h — cache in memory with TTL, don't re-fetch on every call
- Call `GET https://open-api.guesty.com/v1/rate-strategies` to retrieve all rate strategies
- Map the response to a clean internal `RateStrategy` TypeScript interface:

```typescript
interface RateStrategyRule {
  type: 'season' | 'holiday' | 'occupancy' | 'dayOfWeek' | 'gapFill' | string;
  name?: string;
  dateRanges?: Array<{ startDate: string; endDate: string }>;
  adjustment?: { type: 'percent' | 'fixed'; value: number };
  minNights?: number;
  conditions?: Record<string, unknown>;
}

interface RateStrategy {
  id: string;
  name: string;
  description?: string;
  rules: RateStrategyRule[];
  assignedListingIds: string[];
}
```

- Return a typed `RateStrategy[]` array — this becomes the input to the Playwright recreation step

## Step 2 — Playwright Auth Flow

In `src/migrator/guestyAuth.ts`:

- Accept `{ email, password }` and a Playwright `BrowserContext`
- Navigate to `https://app.guesty.com/login`
- Fill email, fill password, click submit
- Wait for navigation away from `/login` — confirm by checking URL no longer contains `/login`
- On failure (e.g., wrong credentials, 2FA prompt detected), throw a descriptive error — do NOT retry with credentials
- Return the authenticated `Page` object
- **Never log the email or password at any point**

---

## Step 3 — Extract Rate Strategies via UI (fallback validation)

In `src/migrator/extractStrategies.ts`:

- Navigate to `https://app.guesty.com/revenue-management/rate-strategy` (or the equivalent deep link)
- Wait for the strategies list to load
- For each strategy row, extract: name, description, number of rules
- Use this as a **validation cross-check** against the Open API response — if the counts don't match, log a warning and proceed with the Open API data as source of truth
- This step is optional/configurable via `ENABLE_UI_VALIDATION=true` env var

---

## Step 4 — Recreate Rate Strategies in Destination Account

In `src/migrator/createStrategies.ts`:

This is the core automation. For each `RateStrategy` in the source array:

1. Navigate to the Rate Strategy section in the destination account
2. Click "New Rate Strategy" (or equivalent button — use `getByRole('button', { name: /new rate strategy/i })` for resilience)
3. Fill in the strategy name and description
4. Save the strategy skeleton
5. For each rule in `strategy.rules`, click "Add Rule" and fill in the appropriate fields based on `rule.type`:
   - **Season rule:** name, start date, end date, price adjustment (% or fixed), min nights
   - **Occupancy rule:** threshold %, adjustment %, lead time settings
   - **Day of week rule:** select applicable days, adjustment
   - **Gap fill rule:** gap length, min nights override
6. Save after each rule addition — don't batch to reduce failure blast radius
7. After all rules are added, log success for that strategy
8. If any individual rule fails, log the error with the strategy name and rule index, and continue to the next rule (partial migration is better than full abort)

**Selector strategy (resilience-first):**
- Prefer `getByRole`, `getByLabel`, `getByText` over CSS selectors
- Use `getByTestId` where `data-testid` attributes are available
- Avoid `nth()` positional selectors — too brittle
- All `fill()` and `click()` calls are wrapped in `expect(locator).toBeVisible()` waits before interaction

## Step 5 — Job Queue & API Layer

### Bull Queue (`src/jobs/migrationQueue.ts`)
- Create a Bull queue called `rate-strategy-migration`
- Queue is backed by Redis — use `REDIS_URL` env var
- Job payload structure:
```typescript
interface MigrationJobPayload {
  jobId: string;
  sourceCredentials: { encryptedEmail: string; encryptedPassword: string; clientId: string; clientSecret: string };
  destCredentials: { encryptedEmail: string; encryptedPassword: string };
  requestedAt: string;
}
```
- Encrypt `email` and `password` fields using AES-256-GCM before enqueuing
- Worker decrypts them in-memory immediately before use, does not store decrypted values

### Express API (`src/api/routes.ts`)
- `POST /api/v1/migrations` — trigger a migration job
  - Request body validated with Zod:
    ```typescript
    z.object({
      sourceClientId: z.string().min(1),
      sourceClientSecret: z.string().min(1),
      sourceEmail: z.string().email(),
      sourcePassword: z.string().min(1),
      destEmail: z.string().email(),
      destPassword: z.string().min(1),
    })
    ```
  - Returns `{ jobId, status: 'queued' }`
- `GET /api/v1/migrations/:jobId` — poll migration status
  - Returns `{ jobId, status: 'queued' | 'running' | 'completed' | 'failed', progress, errors[] }`
- Apply `express-rate-limit`: max 5 requests/minute per IP on `POST /api/v1/migrations`

## Browser Lifecycle Management

In `src/utils/browser.ts`:

- Launch a single `chromium` browser instance at worker startup (not per-job)
- For each job, create a new isolated `BrowserContext` via `browser.newContext()`
- Close the context after the job completes (success or failure)
- On failure, capture a screenshot to `/tmp/migration-failure-{jobId}.png` for debugging
- Implement a cleanup cron that deletes `/tmp/migration-failure-*.png` files older than 24h
- If the browser crashes, relaunch it automatically before accepting the next job

```typescript
// Key pattern
const browser = await chromium.launch({ headless: process.env.HEADLESS !== 'false' });
const context = await browser.newContext({
  viewport: { width: 1280, height: 800 },
  userAgent: 'Mozilla/5.0 (compatible; GuestyMigrate/1.0)',
});
// ... run job ...
await context.close(); // always, in finally block
```

## Logging

In `src/utils/logger.ts`:

```typescript
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',
  redact: {
    paths: ['password', 'email', 'token', 'clientSecret', 'clientId', 
            'encryptedEmail', 'encryptedPassword', '*.password', '*.email',
            '*.token', '*.secret'],
    censor: '[REDACTED]',
  },
});
```

- Use structured logging with `jobId` as a child logger field for all migration steps
- Log: job start, each strategy name being processed, each rule type being added, job completion, errors
- Never log raw credential objects, page content, or cookies

## Error Handling

- `StrategyNotFoundError` — source account has 0 strategies
- `LoginFailedError` — Playwright could not authenticate (wrong credentials, 2FA, account locked)
- `UIChangedError` — expected button/form element not found after 15s timeout (selector may have changed after Guesty UI update)
- `PartialMigrationError` — some strategies succeeded, some failed — include details in job result
- All errors populate the `errors[]` array on the job status response — never swallow silently

## Dockerfile

Use the official Playwright Docker base image which includes all Chromium system dependencies pre-installed and configured securely:

```dockerfile
FROM mcr.microsoft.com/playwright:v1.44.0-noble
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
ENV NODE_ENV=production
ENV HEADLESS=true
USER pwuser
CMD ["node", "dist/index.js"]
```

Note: The `pwuser` non-root user is built into the official Playwright image — this ensures the Chrome sandbox works correctly without `--no-sandbox`.
